# Agent Report

A tiered Markdown summary in `<resultfolder>/<code>/report/`, written for an
agent (or a hurried human) that has neither the repository nor a cluster. It is
a second rendering of the data `show_summary()` prints, not a separate
analysis, and is generated by `bexhoma/report_writer.py`.

```sh
python tpch.py run ... -rp            # any entry script; experiment.py always writes it
bexhoma summary -e <code> -rp         # regenerate from local files, no cluster needed
```

## Tiers

| Tier | Files | Read when |
|---|---|---|
| 1 Answers | `index.md` | always, first; often the only file needed |
| 2 Evidence | `workflow.md`, `loading.md`, `benchmarking.md`, `monitoring.md`, `connections.md` | a value is needed, or a failed test must be traced to a phase |
| 3 Diagnosis | `files.md` and the raw files it links | tier 2 does not resolve the question |

## `index.md`

In order:

1. Frontmatter: `schema_version`, code, workload type, active phases,
   pass/fail/skip counts, written sections.
2. Workload: what ran, with which parameters.
3. How to read the report, the tier table, and the naming rule.
4. Validity-first rules: which failed test restricts which metric, and where
   to check.
5. Tests: every check with passed, failed or skipped.
6. Key Metrics: the benchmark's headline columns per phase.
7. Monitoring: peak CPU and RAM per component.
8. Health Summary: restarts with reason and data loss, SQL errors and
   warnings, how many phases completed every query, missing metrics.
9. Failure Timeline: failures in the order they began, each placed in the
   phase that was running: SUT restarts for every benchmark, plus
   benchmark-specific failures (TPC-H: queries that failed in some pods).
   It orders evidence and claims no causes.
10. Interpretation rules: compare within one code, start from the first
    failure, partial results are results, report variance, cite files.
11. Links to the tier-2 pages that were written.

## Tier-2 pages

- `workflow.md`: planned against actual jobs and pods per phase.
- `loading.md`: loading times and throughput per run.
- `benchmarking.md`: Per Connection and Per Phase results, plus for TPC-H:
  - a note under every pooled table saying which queries it leaves out. The
    pooled totals count only queries that succeeded in every connection of
    the experiment, so one failure anywhere removes a query from every row;
  - Query Completion per Phase: `completed/pods` per phase and query;
  - Per Phase (Complete Phases Only): the same metrics over the phases in
    which every pod completed every query, so the clean phases of a partly
    failed run still show;
  - latency per query, and the same over the complete phases only when some
    phase is incomplete; errors with messages, warnings, EXPLAIN plans.
- `monitoring.md`: CPU and RAM per component and phase, missing metrics with
  whether the zeros are expected, application metrics, and the full catalog of
  every collected metric.
- `connections.md`: SUT restarts with reason, exit code, data volume and links
  to the describe log and the crashed instance's log; then the parameters of
  every connection, each listed once where it stops varying (all connections,
  one configuration, one connection).

## `files.md` and provenance

`files.md` links every raw file in the result folder exactly once, grouped by
kind, each group with a one-line note on what it holds. It is built by listing
the folder, so it never links a missing file nor misses one. Each tier-2 page
ends with a Provenance footer naming the `files.md` groups behind it. The agent
can open a raw file only through such a link. `agent_summary.yml` is never
linked: it is an earlier verdict, not evidence.

## How it is built

`show_summary()`'s hooks return a tree of `Section` objects (heading,
DataFrame, lines, children) instead of printing. Two renderers consume the same
tree: `render_stdout()` prints the terminal summary, `write_markdown_report()`
writes the tiers and links connection names to `connections.md`. Every
DataFrame is fetched once.

Benchmark-specific content lives on the benchmark class, not in the report
writer: `_build_key_metrics_section()` names the headline columns,
`_results_notes()` and `_build_completion_sections()` add the TPC-H notes and
completion tables, and `extra_context["failure_events"]` feeds the Failure
Timeline.
